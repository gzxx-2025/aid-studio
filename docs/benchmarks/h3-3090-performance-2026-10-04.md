# MiniMax H3 / ComfyUI RTX 3090 性能诊断记录

日期：2026-10-04
主机：`10.190.0.222`
原则：不修改已保存的生产 workflow；基准任务使用生产图的临时副本。

## 1. 当前实际环境

- GPU：2 × RTX 3090 24 GB；ComfyUI 固定使用 GPU 0。
- GPU 0 同时驻留 OmniVoice TTS（约 4.3 GB）、ASR（约 2.4 GB）及少量其他进程，H3 启动前约 7 GB 显存已被占用。
- GPU 0 当前 PCIe 链路为 x8（硬件上限 x16）；GPU 1 被 Qwen3.8 llama-server 基本占满。
- `nvidia-smi topo -m` 显示两张 3090 之间为 `SYS`（跨 PCIe Host Bridge 与 NUMA 互联），没有 NVLink；GPU 0 在 NUMA 0，GPU 1 在 NUMA 1。把单个 H3 DiT 做跨卡 tensor parallel 会增加跨 NUMA/PCIe 通信，不建议作为首选加速。若释放 GPU 1，更适合“一卡 H3、另一卡 Text Encoder/VAE/超分”的流水线隔离，或两卡各跑一个独立任务。
- GPU 0 位于 NUMA node 0，但 ComfyUI 未设置 CPU/内存亲和性；诊断时 ComfyUI 匿名内存约 19.8 GiB 位于 node 0、约 37.0 GiB 位于远端 node 1。被 offload 的大模型权重很可能经 CPU 间互联再回传 GPU 0。
- 系统内存 125 GiB；诊断时 swap 已使用约 33 GiB。
- ComfyUI：git `cbbc9dab`；PyTorch `2.8.0+cu128`；CUDA runtime 12.8；驱动 595.91.07。
- ComfyUI 启动参数：`--cuda-device 0 --cpu-vae --disable-async-offload --reserve-vram 4`。
- 启动日志明确显示 `Using pytorch attention`。
- `sageattention 1.0.6` 已安装，但生产图未连接 `MiniMaxH3SpeedCache`，扩散阶段没有启用 SageAttention。QwenVL 路径运行时因 head dimension 不兼容回退到 PyTorch attention。
- FlashAttention、xFormers、Sparse/Sol-Attn 当前未安装。
- PyTorch 2.8/cu128 下 ComfyUI 日志提示优化 CUDA 量化算子要求 cu130 或更高；当前量化模型使用 eager 路径。
- 最近 24 小时日志还出现 4 次采样初始化阶段的 `Allocation on device` 失败；这与 GPU 0 上长期驻留约 7 GB 的其他服务、模型动态装载和显存余量过小一致。当前基准本身未发生 OOM。

## 5. 初步瓶颈排序

1. H3 Transformer 扩散：约 17 分 30 秒，当前 attention/量化内核没有得到预期加速。
2. 模型初始化与 CPU↔GPU 分阶段装载：约 4 分 36 秒；GPU 0 被其他服务占用约 7 GB，另有 4 GB ComfyUI 预留，导致 20–26 GB 模型无法常驻。
3. Text Encoder/参考图编码：约 3 分 20 秒；QwenVL SageAttention 实际 fallback，且 32B 编码器发生 offload。

附加放大因素：GPU 0 仅运行在 PCIe x8，且 ComfyUI 大部分 CPU 内存页落在 GPU 0 的远端 NUMA node 1；这会进一步放大每步权重回搬成本。

音频 VAE、视频 VAE 和封装合计约 126 秒，是次要瓶颈，但 FAST 模式关闭原生音频仍可节省约 1 分钟并降低内存压力。

上述 126 秒只适用于 GPU tiled video VAE 基准图；旧 AID 生产图的 CPU、非分块 video VAE 尾部耗时明显更长，待当前生产任务结束后按历史时间戳补录。

## 6. 低步数与 Attention 对照结果

全部使用相同提示词、seed、243 帧、24 FPS 和参考图；均为临时图，未修改生产 workflow。

| 组 | 分辨率 | Steps | Attention | 总时间 | 相对 A | 观察 |
|---|---:|---:|---|---:|---:|---|
| A | 832×480 | 20 | PyTorch | 1620.3 秒 | 1.00× | 质量基线 |
| B | 832×480 | 8 | PyTorch | 531.7 秒 | 3.05× | 暖模型、重新做主要 conditioning；人脸、构图与动作连续性肉眼仍可用 |
| C | 832×480 | 6 | PyTorch | 366.7 秒 | 4.42× | 暖模型且 conditioning 命中缓存；细节略有变化 |
| C-Sage | 832×480 | 6 | SageAttention 1.0.6 | 309.5 秒 | 5.23× | 暖模型且 conditioning 命中缓存；比 C 再快 15.6% |
| R-low | 736×416 | 8 | PyTorch | 351.7 秒 | 4.61× | 比同为 8 步的 B 快 33.8%；细节降低但适合候选 |
| R-720 | 1344×768 | 8 | PyTorch | 24.2 秒后 OOM | — | 24 GB + 约 7 GB 常驻服务下不可用 |

Sage 组的 Speed Cache 阈值设为 0，因此没有跳过任何 Transformer pass；日志明确记录 `skipped 0/6`。该 15.6% 提升来自 attention backend，而不是缓存“偷步”。Qwen3-VL 编码器的 SageAttention 仍因 head dimension 不支持而 fallback，只有 H3 DiT 扩散部分成功使用 Sage。

上述 5分07秒是同一提示词/参考图连续测试时的**暖路径**，不能直接当成任意新镜头的冷启动时延。一次冷复测在系统同时复制 11GB Conda 环境和下载 22GB 模型时，CPU conditioning 超过 7 分钟仍未进入 GPU 扩散，结果因 I/O/内存竞争被主动中止，不计入正式基准。这进一步证明：conditioning cache、暖 Worker、清理 swap 压力和 H3 作业资源隔离，是把真实生产稳定在几分钟级的必要条件。

四帧接触表人工检查显示：20、8、6 和 Sage-6 都保持单人、白衣、室内和连续转头/移动的主语义；6 步和 Sage-6 在床铺、窗框和面部微细节上有变化，但未出现明显破面。该结论只覆盖当前中等动作样例，正式切换前仍需增加快动作、双人交互、手部和对白样例。

普通基础模型的 4-step 仍不执行：它没有经过 4-step 蒸馏，强行降低会把速度收益换成不可控质量损失。

## 7. 当前可落地的两个生产 Preset

### FAST（候选镜头）

- 无参考图 T2VA：优先官方 FastH3 8-Step V2，`736×416` 或 `832×480`，cu130 + VSA；10 秒暖路径已实测约 2 分 41 秒。
- 需要人物/商品参考图：基础 H3 Ref2VA，`736×416` 或 `832×480`，6 steps，`res_multistep + simple`，H3 DiT 使用 SageAttention。
- 视频 VAE：GPU FP16 tiled decode；禁止落回普通 CPU `VAEDecode`。
- 原生音频：候选阶段可关闭，定稿后再生成/后配；预计还可省约 1 分钟。
- 预计 10 秒暖路径：FastH3 T2VA 约 2.7 分钟；基础 Ref2VA 约 4–6 分钟。全冷 FastH3 cu130 首次运行约 11 分钟，必须通过暖 Worker 和 conditioning cache 避免按镜头重复支付。

### QUALITY（定稿镜头）

- 基础 H3：`832×480` 8–12 steps 起步；复杂动作、多人或关键特写再升至 20 steps。
- 近 720P 不在当前共享 3090 上直接做 10 秒；优先 832×480 生成后做视频超分，或拆成 4–5 秒短段。
- 多参考图/角色一致性使用基础 Ref2VA；不能直接换成只支持首尾帧的蒸馏模型。

## 8. 2026-10 可用的新加速路径

### 8.1 官方 FastVideo FastH3 8-Step V2（影子测试已通过）

ComfyUI 官方现已支持 DMD2 蒸馏的 FastH3 8-Step V2：固定 8 steps、video/audio shift `10/3`、`res_multistep + simple`，并使用 VSA 从 20% 调度位置开始仅保留 10% attention。官方已提供 `fastvideo_fasth3_8step_v2_pruned_int8_convrot.safetensors`（22.1 GB），现有 H3 Text Encoder 和 VAE 可复用。

限制：

- 要求 ComfyUI 0.36.0+；当前生产为 0.31.0，不能原地替换。
- 上游 FastVideo 模型卡与当前 ComfyUI 模板内说明均明确写为只支持 T2VA；FL2VA 与 Ref2VA 没有参与蒸馏。ComfyUI 文档页另有“首尾帧 I2V”描述，存在版本不一致，因此影子测试按更保守的上游范围处理，不把 I2V 当作已支持能力。
- 官方明确说明速度版会牺牲部分复杂运动和音频质量，适合草稿/候选，不应无条件替换 QUALITY。

落地状态：独立影子 ComfyUI、官方模型校验、5 秒与 10 秒输出、cu130/VSA 均已验证通过；生产 `8188`、现有模型和 workflow 均未修改。FastH3 先仅用于不依赖角色参考图的空镜、环境镜、转场和候选草稿；需要角色/商品一致性的镜头继续使用基础 Ref2VA 6/8-step 路径。等上游发布 Omni Ref 或经实测确认 FL2VA 可用后，再扩大范围。

### 8.2 SageAttention 2.2 / 2++（适合 RTX 3090）

当前 1.0.6 已在 H3 DiT 上实测带来 15.6% 端到端提升。官方 SageAttention 2.2/2++ 支持 Ampere 与 CUDA 12，值得在影子环境继续验证；SageAttention 3 的 FP4 内核面向 Blackwell，不适合 RTX 3090。

官方资料：<https://github.com/thu-ml/SageAttention>

### 8.3 Comfy/PyTorch cu130 量化内核

影子环境已使用 PyTorch `2.9.1+cu130` 验证：Comfy Kitchen CUDA backend 从 `disabled=True` 变为 `disabled=False`，FastH3 VSA 从回退稠密变为实际 `sparse producer path`。832×480、10 秒暖路径从 cu128 的 346.22 秒降到 cu130 的 161.05 秒。生产仍保持 PyTorch 2.8/cu128，不能在没有回归测试和一键回退前原地升级。3090 不应选 NVFP4 作为主路径，它没有 Blackwell 原生 FP4 吞吐优势。

### 8.4 Layer-wise offload 与组件顺序装载

FastVideo 对单 GPU推荐 `dit_layerwise_offload`：把 PCIe 传输与计算重叠，官方称开销很小；`lazy_module_load` / H3 sequential load 则可将峰值从“Text Encoder + DiT + VAE”降到三者最大值，但每次生成会付出重新读盘代价。对 24 GB 3090，优先级应为：

1. 先释放 GPU 0 上的 TTS/ASR/字幕常驻显存；
2. 再使用 layer-wise offload；
3. 只有仍 OOM 时才对 Text Encoder/VAE 做更重的 CPU offload。

官方资料：<https://github.com/hao-ai-lab/FastVideo/blob/main/docs/inference/offloading.md>

### 8.5 任务级缓存、形状桶与暖 Worker

- 以“模型版本 + prompt + 参考图 hash + 几何尺寸”缓存 Qwen3-VL conditioning，重复 seed/steps 时不重复编码。
- 将生产尺寸限制在少数桶（736×416、832×480），有利于 `torch.compile` 图复用和减少模型/内核抖动。
- H3 运行期间保持同一暖 Worker，避免每镜重复 3–5 分钟冷加载；但前提是先释放 GPU 0 的约 7 GB 常驻显存。
- 扩散完成后先释放 DiT，再做 GPU tiled VAE；音频/封装可进入独立后处理队列，防止 GPU 队列被 CPU 尾部阻塞。

### 8.6 两阶段“低分辨率草稿 + 轻量精修”

NVIDIA 2026-08 公布的 H3 Super Acceleration 使用 4-step H3 在 `896×512` 生成草稿，再由 LTX 做 3-step 高分辨率精修。这一思路比“直接让 H3 原生跑 720P/1080P”更适合消费卡，但其公开秒级成绩来自 GB200，不能照搬到 RTX 3090。

3090 上建议先做保守变体：FastH3/基础 H3 在 736×416 或 832×480 生成运动与构图，再进入现有视频超分/人脸轻修；只有该链路画质不足时，才在另一个影子环境评估 LTX-2.5 三步 refiner。这样即使精修不理想，也可以直接回退到原始 480P 视频，不影响主生成链路。

官方资料：<https://nvlabs.github.io/Sana/Sol-Engine/H3-Super-Acceleration/>

### 8.7 暂不进入生产的方案

- **Sol Engine / Sol-Attn 全栈**：最新结果很强，但主要针对 GB200、B300、H100、A100、RTX 5090；3090 缺少其 FP8/NVFP4 与新架构内核优势。可借鉴“融合、缓存、稀疏、两阶段”的方法，不直接套用其延迟数字。
- **社区 Sparse/Sol-Attn 节点**：可能继续降低 attention 时间，但完整视频可能出现闪烁、时序脉冲或角色漂移。必须用快动作、手部、多人和长镜头做 A/B，不能只看单帧或 attention tensor 误差。
- **First-block / residual cache、Spectrum forecasting**：属于近似跳步；适合草稿，但要记录实际跳过的 pass、连续复用次数和画质差异。当前阈值 0 的 Speed Cache 实测跳过 `0/6`，因此尚未使用这种近似。
- **TAEH3/Tiny VAE**：适合生成中的低成本预览和前端进度可视化，不建议直接作为最终解码；当前正确 GPU tiled VAE 只占约 35 秒，不是首要瓶颈。
- **两张 3090 做单任务 tensor parallel**：当前两卡为 `SYS`、无 NVLink且分属不同 NUMA node，通信成本很可能抵消收益。释放 GPU 1 后应优先做双 worker 并发或组件级流水线，而不是拆一个 Transformer 到两张卡。

## 12. FastH3 热驻留与低分辨率 VSA 验证（2026-10-11）

已将 FastH3 影子实例改为用户级 systemd 常驻服务，并为 `fast_vsa` 单独设置 6 小时热驻留窗口；通用 H3 缓存仍保持 1 小时。VSA 的 `min_tokens` 从 12288 调整为 8192，使 736×416、5 秒任务的 11616 tokens 能进入稀疏路径。运行日志确认采样调度开始后实际出现 `BlockSparseAttention: sparse producer path`，不是仅安装成功后回退稠密 attention。
